# Architecture

## Shape of the system

Three layers, each readable without the others:

1. **Data.** Plain UTF-8 CSV registers and markdown records in a program workspace. Git is the shared state. No database.
2. **Engine.** The `pmf` package. It loads the profile and the lifecycle definitions, checks each command against the guards, writes the change, and appends one row to `events.csv`.
3. **Presentation.** Markdown drafts, the generated HTML dashboard, and the skills that drive the command line. None of these change data except through the engine.

## Flow of a change

```
command  ->  load workspace and profile  ->  check the entity's current state
         ->  evaluate the guards for the requested transition
         ->  refused?  print the guard that refused, write nothing, exit non-zero
         ->  allowed?  write the register row  ->  append events.csv  ->  exit 0
```

`--dry-run` stops after the guard check and prints the change. A refused command never leaves a partial write.

## Where the rules live

| Rule | Defined in | Enforced by |
|---|---|---|
| States and transitions | `pmf/data/lifecycles.json` | `pmf/lifecycle.py` |
| Guards (what a transition needs) | `pmf/data/lifecycles.json`, implemented in `pmf/guards.py` | `pmf/lifecycle.py`; a refusal test per guard |
| Thresholds, phases, gates, severity, approval tiers | the program profile (`profiles/*.json` copied into the workspace) | `pmf/profile.py` |
| Metrics | `pmf/metrics.py`, thresholds from the profile | `pmf health`, dashboard |
| Register schemas | `pmf/schemas.py` | `pmf check`; documented in `docs/DATA_SCHEMAS.md` |

The rule that matters most: a number that a person sets lives in the profile, and a rule that a person cannot override lives in the code. The consistency tests read the profile and the documents, so the two cannot quietly disagree.

## Why no third-party packages

The tool runs anywhere Python 3.8 runs, on a locked-down laptop, with no install step beyond copying the folder. The cost is some boilerplate in the CSV handling and the HTML generation. The dashboard is one self-contained file with no network request, so it can be opened offline and attached to an email without leaking anything it did not already contain.

## Generated files

Some files are produced by tools, and the tests check that the committed copy matches a fresh run:

| File | Generated by | Check |
|---|---|---|
| `docs/LIFECYCLES.md`, lifecycle diagrams | `tools/gen_lifecycles.py`, `tools/gen_diagrams.py` | `gen_lifecycles.py --check` |
| Templates (CSV headers, document skeletons) | `tools/gen_templates.py` | `gen_templates.py --check` |
| The Meridian example | `examples/run_demo.py` | `run_demo.py --check` |
| Explainer HTML | `tools/gen_explainer.py` | `test_diagrams_explainer.py` |

Edit the generator, not the output.

## Privacy gate

`tools/privacy_scan.py` runs before any release. It scans every file, the contents of office and archive files, file names, document metadata, and git history against a denylist that is kept outside the repository. Its `selftest` plants fictional leaks and confirms the scanner catches each one. The scanner finds only what its denylist and patterns describe, so a clean scan is necessary, not sufficient; the manifest must also be read by a person.

## What is deliberately absent

No connectors, no network calls, no scheduling engine, no forecasting, no multi-user locking. See [SCOPE.md](SCOPE.md).
